# ResearchFlow AI v1.2.0 Implementation Plan

## Goal

Make the production architecture match the code that actually runs, strengthen async job execution, and raise test depth without adding unrelated product features.

## Non-goals

v1.2.0 will not add RAG, LangGraph, LangChain, LlamaIndex, OpenAI Agents SDK orchestration, Redis, Celery, Kubernetes, authentication, distributed tracing, or other major product features. Those remain future work unless they become real runtime dependencies.

## Target runtime

Frontend

## Architecture changes

### Application core

Move the real research execution code from `app/agents/` into `app/workflow/`:

- `agents/orchestrator.py` -> `workflow/orchestrator.py`
- `agents/planner.py` -> `workflow/planner.py`
- `agents/search_agent.py` -> `workflow/researcher.py`
- `agents/summarizer_agent.py` -> `workflow/analyst.py`
- `agents/report_agent.py` -> `workflow/reporter.py`

Use workflow terminology in persisted step labels where doing so does not break compatibility.

### Runtime truth

Remove empty or conceptual modules from the production package. Future/experimental designs belong under `docs/future/`.

Move documentation for:

- RAG
- OpenAI Agents SDK
- LangGraph / LangChain / LlamaIndex adapters
- observability/evaluation expansion

The `/api/capabilities` endpoint must report implemented runtime capabilities only.

### Services

Keep external boundaries explicit:

```text
services/
|- llm/
|  |- service.py
|  |- gemini.py
|  `- openai_compatible.py
|- search.py
|- citations.py
`- errors.py
```

Provider-specific transport belongs outside workflow modules.

### API

The API accepts work; the worker executes work.

- Remove production execution through FastAPI `BackgroundTasks`.
- Canonical creation flow: POST -> persist `queued` -> return immediately.
- Remove or deprecate `run_now` rather than maintaining a second executor path.
- Remove duplicated job-list semantics where practical.
- Return consistent 404 responses for child resources when the parent job does not exist.
- Centralize readiness/evaluation scoring.

### Job lifecycle

Canonical states:

```text
queued -> in_progress -> completed
                     `-> failed
```

`pending` is legacy compatibility only and should not be newly written.

Job claiming must be explicit and atomic. Multiple workers must not execute the same queued job.

### Persistence

Add a new Alembic migration rather than editing the v1.1.0 migration history.

Strengthen constraints where existing data permits it, including required foreign keys and required report/source fields. Any constraint change must be migration-safe for existing databases.

### Error handling

- Preserve user-safe errors on expected provider/workflow failures.
- Log or otherwise retain actionable internal failure context without exposing secrets to API clients.
- Ensure failed jobs reach a terminal state reliably.

## Tests

Organize tests by responsibility:

```text
backend/tests/
|- unit/
|  |- workflow/
|  `- services/
|- integration/
|  |- test_research_api.py
|  |- test_worker.py
|  `- test_persistence.py
`- e2e/
   `- test_research_flow.py
```

Required coverage:

- workflow planning/research/analysis/report behavior
- LLM provider selection and fallback
- search errors
- API job creation and reads
- canonical state transitions
- worker atomic claiming / duplicate-execution protection
- workflow failure -> failed job
- persisted steps, sources, and report
- 404 behavior for missing parent jobs
- readiness scoring from one implementation
- migration boot path
- frontend submit/poll/completed/failed behavior

## Production configuration

- Development defaults may remain convenient.
- Production documentation must require explicit CORS configuration.
- Production command must not use Uvicorn `--reload`.
- API and worker remain gated on successful Alembic migration.

## Release gate

v1.2.0 is releasable only when:

- backend tests pass
- frontend checks/tests/build pass
- Alembic upgrade succeeds from a clean database
- upgrade succeeds from the v1.1.0 schema
- Docker/Compose validation succeeds
- one full queued-job -> worker -> completed-report smoke test succeeds
- failure-path smoke test leaves the job in `failed`
- README architecture matches actual runtime
- no experimental capability is advertised as implemented
